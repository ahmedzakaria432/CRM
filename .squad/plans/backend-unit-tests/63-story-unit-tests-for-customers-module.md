## Test conventions (apply to every slice)

- Namespaces mirror folders: `Crm.Modules.Customers.Tests.Domain`, `…Tests.Application.Commands.AddContact`, … Class name = production type + `Tests`. **Name clashes:** a Support class named `Customers` would collide with the `Crm.Modules.Customers` namespace (UT-03 pitfall) — the fixtures class is `CustomerFixtures`. Inside `Crm.Modules.Customers.Tests.Domain` the type `Customer` resolves fine; if any ambiguity with a namespace segment appears use a `using` alias (`using CustomerAggregate = Crm.Modules.Customers.Domain.Customer;`). The domain `EmailAddress` / `PhoneNumber` / `LocalizedText` types are not ambiguous with FluentValidation (which only has an `EmailAddress()` extension method).
- Domain errors: `Assert.Throws<DomainException>(…).Error.Code` (string literals). Result failures: `result.IsFailure`, `result.Error.Code` **and** `result.Error.Type` through a copied `Expect.Failure(result, code, ErrorType.X)`.
- Command/query handlers get a **substituted** `IRepository<Customer, CustomerId>`, `ICustomersUnitOfWork`, `ICurrentUserService`, `ICustomerNumberGenerator`, `IDateTime` (`Clock.Fixed()`), `IEventBus`. `Task<Customer?>` repository returns use `Returns(Task.FromResult<Customer?>(x))` via the copied `Holds`/`Finds` helpers; `SaveChangesAsync` is asserted `Received(1)` on commit paths and `DidNotReceive()` on every failure path; `SetOriginalRowVersion(customer, bytes)` is asserted **before** the mutation (record call order in a list, not `Received.InOrder` — UT-03 pitfall); `ListAsync`/`CountAsync` stubs go through `Arg.Any<Specification<Customer>>()` helpers (copy of `Stubs.Lists`/`CountsAs`) with the specification captured via `Arg.Do` for type checks.
- Handlers operate on **real `Customer` aggregates** built by `CustomerFixtures` (the aggregate is the unit under test too); the Customer Id/contact/note ids are fixed constants in `Ids`.
- Validators: `validator.Validate(command)`; assert `IsValid` and the failing `PropertyName`s through copied `Expect.Valid/Invalid`; validators with `ILocalizationService` get `FakeLocalization.Keys()` for structure and `FakeLocalization.Resources()` (real `.resx`, manager name `Crm.Modules.Customers.Application.Localization.Resources.CustomersMessages`, assembly of `CustomersCacheKeys`) for the message-text checks.
- `[Theory]` over cases instead of loops, one InMemory database name per test, no static mutable state in `Support/`, culture-changing test classes use `UiCulture` + a `[Collection]`.

## Edge Cases & Failure Modes

- **Result vs exception.** Expected business failures are Results (`NotFound` for customer/contact/note, `Forbidden` `Organisation.OutOfScope` and `Validation` `Organisation.DepartmentRequired` from `CreateCustomer`); aggregate invariants (all 25 `Customers.*` 422 codes) are `DomainException`s that propagate out of handlers. Each test asserts the right one of the two.
- **Out-of-scope customer ids are not a handler concern.** Handlers see `null` for an unknown id; an out-of-scope id makes `Repository.GetByIdAsync` throw before the handler continues (403 by the pipeline). Handler tests assert 404 for `null`; the scope behaviour is asserted once, in `CustomerRepositoryScopingTests` and `CustomersDbContextTests`.
- **Handlers do not re-validate.** Input the validator would have stopped (unknown `Type` string, `fr` language, 21 contacts, malformed sort) reaching a handler surfaces as an `ArgumentException` (`Enum.Parse`), a `DomainException`, or a silent fallback (`SearchCustomers` sort → `CreatedAt`); pinned by name.
- **Duplicate warning order.** Value objects are built **before** the duplicate lookup (malformed → 422 first, plan 11 line 1817); the lookup uses normalised distinct values; with `ConfirmDuplicate` the in-request duplicate is still rejected by the aggregate (the number is already drawn — a gap, by design).
- **Concurrency.** Profile, status and contact handlers call `SetOriginalRowVersion` with the client's bytes **before** changing the aggregate; note handlers never do. The 409 itself is not reproducible on InMemory (UT-01/UT-02); assert the call and its order only. `Revision` is the aggregate-level reason contact-only changes touch the root row.
- **Integration events.** Published from the handler **after** `SaveChanges` (`Received` order recorded in a list); never on a failure Result or a `DomainException`; contact and note handlers publish nothing. `Id` is a fresh `Guid` per publish.
- **Scope-lifted lookups.** `PortalContactsSpecification` lifts **only** the scope filter (tenant/branch/department); soft-delete stays. Tests use a caller whose scope would hide the row (another tenant, `OrganisationScope.None`) to prove the lift.
- **Internal types.** `CustomerDomainErrors`, `CustomersErrors`, `ContactChannels`, `PortalContactMapper`, `DuplicateCandidates` are `internal` with no `InternalsVisibleTo`; they are covered through the aggregate, the handlers and the module API. Adding `InternalsVisibleTo` is a production change and not allowed here.
- **Floating clock.** Never `UtcNow`; note timestamps use `Clock.Now` and `Clock.Later(n)`.
- **Parallelism.** One InMemory database name per test; no static mutable state; culture-changing tests in a `[Collection]`.

Probe `SearchCustomersQueryHandlerTests` first; where InMemory cannot evaluate a spec, fall back to `Stubs.Matching` over a list (evaluating the specification's criteria/order/paging in memory) and assert the scope isolation in `CustomersDbContextTests`. Record the fallback.
- **R5 — Localised messages.** The `ar` satellite resource of `CustomersMessages` must be copied to the test bin; asserting the Arabic text needs `UiCulture.Use("ar")` in a `[Collection]`. If it does not load, assert `en` only and record it.
- **R6 — `SqlCustomerNumberGenerator` and `CustomersDbContext` model.** `SqlQuery<long>(NEXT VALUE FOR …)` needs SQL Server and is not tested (recorded as not unit-testable). `modelBuilder.HasSequence<long>` must not throw on the InMemory provider when the model is built; if it does, `CustomersDbContextTests`/`CustomersSeederTests`/handler InMemory tests cannot run and the plan falls back to substituted repositories plus the list evaluator for every query test (record in the tracker; do not change `src/`).
- **R7 — Behaviours the plan could not settle by reading.** `CustomerNumber.FromSequence(long.MaxValue)` (length vs `MaxLength` 20), `PhoneNumber` with Arabic-Indic digits (`\d` in .NET), `AddContact` with a blank name and a duplicate email (duplicate reported first), `Enum.Parse` accepting numeric strings and throwing `ArgumentException` for unknown names (handlers), `CreateCustomerCommandValidator` / `GetCustomerNamesQueryValidator` with a null list (`NotNull().Must(...)` does not stop at `NotNull`, likely `NullReferenceException`), `UpdateCustomerCommand` with a null `RowVersion`. Assert the **actual** outcome, pin it by name, list each in Follow-ups.
- **R8 — Case sensitivity.** Search/lookup are case-sensitive on InMemory (production relies on the SQL Server collation): same-case matches only, pinned.
- **R9 — Scope lift on InMemory.** `Specification.IgnoreOrganisationScope()` is honoured by `Repository` through `IgnoreQueryFilters([ModuleDbContext.ScopeFilterName])`; the portal-lookup tests rely on InMemory supporting **named** query filters (EF Core 10). The seeder's `IgnoreQueryFilters([SoftDeleteFilterName, ScopeFilterName])` has the same dependency. If named filters are not honoured, assert the specification flag only and record the gap.
- **R10 — Owned-collection persistence on InMemory.** `ValueGeneratedNever()` for `Contact.Id`/`CustomerNote.Id` matters only for relational providers; InMemory will not reproduce the "UPDATE affected 0 rows" failure. Tests assert round trip only.
- **R11 — Runtime.** The whole project should stay at a few seconds (no PBKDF2, no SQL). If the InMemory graph tests are slow, share one seeded database per class through a fixture only if there is no mutation.
