## Test conventions (apply to every slice)

- Namespaces mirror folders: `Crm.Modules.Tickets.Tests.Domain`, `…Tests.Application.Commands.ClaimTicket`, … Class name = production type + `Tests`. **Name clashes:** a Support class named `Tickets` would collide with the `Crm.Modules.Tickets` namespace (UT-03 pitfall): fixtures are `TicketFixtures`. Inside `Crm.Modules.Tickets.Tests.Domain` the type `Ticket` resolves fine; if a namespace segment shadows a type use a `using` alias (`using TicketAggregate = Crm.Modules.Tickets.Domain.Ticket;`).
- Domain errors: `Assert.Throws<DomainException>(…).Error.Code` (string literals). Result failures: `Expect.Failure(result, code, ErrorType.X)` asserting `Code` **and** `Type` (`NotFound`, `Forbidden`, `Validation`, `Domain` (422), `Conflict` (409), `Unauthorized` (401)).
- Handlers get **substituted** `IRepository<Ticket, TicketId>`, `IRepository<Category, CategoryId>`, `ITicketsUnitOfWork`, `ICurrentUserService`, `IDateTime` (`Clock.Fixed()`), `IEventBus`, `ITicketNumberGenerator`, `ICustomersModuleApi`, `IIdentityModuleApi`, `IOrganisationModuleApi`, `IPortalTicketReadModel`, `ITicketReadModel`, `ITicketThreadReadModel`, and a **real** `TicketDtoAssembler` / `PortalTicketMapper` / `TicketRefusals` path (the latter is internal, reached through handlers) built over those substitutes. Real `Ticket`/`Category` aggregates come from `TicketFixtures`.
- `Harness` (copy of Customers') extended with one call log `rowversion`, `add`, `save`, `lookup` (every call on the substituted Identity/Organisation/Customers APIs and the categories repository made by the assembler), `publish`, so "save, then nested reads, then publish" and "`SetOriginalRowVersion` before the change" are asserted without `Received.InOrder` (UT-03 pitfall: it fails when the same substitute is called extra times).
- Localisation: structure tests use `FakeLocalization.Keys()` (echo); detail-text tests use `FakeLocalization.Resources()` over the real pair (manager name `Crm.Modules.Tickets.Application.Localization.Resources.TicketsMessages`, assembly of `TicketsMessageKeys`) and `UiCulture.Use("en"/"ar")` in a `[Collection]`; assert that the detail **contains the (localised) status name**, not the whole sentence (R8). `string.Format` uses `CurrentCulture`, `localization.Get` uses `CurrentUICulture`: set both in `UiCulture`.
- Validators: `validator.Validate(command)`; assert `IsValid` and failing `PropertyName`s through `Expect.Valid/Invalid`; localised messages checked with `Resources()`.
- `[Theory]` over tables instead of loops; one InMemory database name per test; no static mutable state in `Support/`; EF InMemory **cannot run `OrderBy` + `ThenBy` from `SpecificationEvaluator`** (UT-04 R4): evaluate specifications in memory with `Stubs.Matching` over a list (or `SeedGraph.Visible`-style load through the real filters), and only run `OrderBy`-only paths through the real `Repository`.
- Test timestamps: `Clock.Now` = `2026-10-11T09:00Z`, `Clock.Later(minutes)`; fixed Guid ids in `Ids`.

## Edge Cases & Failure Modes

- **Result vs exception.** Expected business failures are Results (`NotFound` for ticket/category, `Forbidden` `Organisation.OutOfScope`, `Validation` `Organisation.DepartmentRequired`, `Conflict` `Tickets.AlreadyClaimed`, `Unauthorized` `Authorization.PortalOnly`, `Domain` 422 for `TransitionNotAllowed`, `CustomerInactive`, `ContactNotOfCustomer`, `AssigneeInactive`, `AssigneeNotInDepartment`, `TargetDepartmentInactive`, `CategoryDepartmentInactive`, and the pass-through of the other modules' failures); aggregate invariants (28 `Tickets.*` codes) are `DomainException`s that propagate out of handlers. Each test asserts the right one of the two (an illegal transition is a Result when the handler asked `TicketRefusals` first and an exception when the aggregate is the backstop).
- **Out-of-scope ids are not a handler concern.** Handlers see `null` for an unknown id; an out-of-scope id makes `Repository.GetByIdAsync` throw (403 by the pipeline). Handler tests assert 404 for `null`; scope behaviour is asserted once in `TicketRepositoryScopingTests` and `TicketsDbContextTests`. **Portal handlers never use `GetByIdAsync`**: not-yours is 404 by construction.
- **Publish is last.** Every publishing handler builds its DTO (nested module reads) before `eventBus.Publish`; the call-log order assertion protects it. Two events for one command (reply that reopens) are published in the order message then status.
- **Handlers do not re-validate.** Input the validator stops (unknown priority/action/status strings, wrong visibility, malformed sort) reaching a handler surfaces as `ArgumentException` from `Enum.Parse`, a `DomainException`, or a silent fallback (`SearchTickets` queue/sort → `All`/`CreatedAt`); pinned by name. Numeric strings (`"1"`, `"2"`) parse in handlers but the validators reject them (`Enum.GetNames` rules).
- **Failure leaves no trace.** After every refused command the aggregate, `Revision`, activity count and event list are unchanged (domain tests) and the unit of work saved nothing (handler tests).

## Risks (named; verify first in task 1.1)

- **R1 — `TicketsDbContext` on InMemory.** `OnConfiguring` adds a `SqlServerOptionsExtension` (`UseQuerySplittingBehavior`); with `UseInMemoryDatabase` EF may throw "multiple database providers". - **R2 — Transitive Contracts flow.** The test project must see `Customers/Identity/Organisation.Contracts` (and the two `DevSeed` classes) only through Application/Infrastructure references. If a symbol does not flow, stop and record; adding a reference is allowed only for the `Microsoft.EntityFrameworkCore.InMemory` package, never another module's project (CRM0001).
- **R3 — InMemory ordering.** `SpecificationEvaluator` applies `OrderBy` + `ThenBy` in `CategoriesSpecification`, `PortalTicketsSpecification`, `TicketSearchSpecification`, which EF InMemory cannot run (UT-04 R4). Evaluate them in memory with `Stubs.Matching`; read-model tests use specs whose order is applied in memory or only the `OrderBy`-free shapes, otherwise they are limited to criteria. MinValue` order: tickets built in memory have **null audit timestamps** unless stamped (`Stamp` helper or the InMemory auditing interceptor).
- **R4 — `ConcurrencyConflictException`.** The `ClaimTicket` race path needs the exception to be constructible from a test (read its constructor in `Crm.BuildingBlocks.Application`; if it requires a `DbUpdateException`, create one with `new DbUpdateException("x", (Exception?)null)` or a substitute-free subclass-free instance). `TicketsDbContext.IsSequenceCollision` needs a real `Microsoft.Data.SqlClient.SqlException` (no public constructor): not unit-tested, recorded.

## Candidate follow-ups spotted while planning (verify against the code, then pin and record; do not change `backend/src/`)

1. `Category.Update` assigns `Name` before validating `DisplayOrder`: a rejected update leaves the new name set on the tracked entity (an always-valid-aggregate gap; harmless if the transaction is abandoned).
2. `ClaimTicketCommandHandler` checks the assignee before the status: an assigned Closed ticket answers 409 `AlreadyClaimed`, an unassigned Closed ticket 422 `TransitionNotAllowed`; `Ticket.Claim`'s `AlreadyAssigned` is unreachable through the handler.
3. `TransitionTicketCommandHandler` `default` branch: a non-transition action that the status allows (e.g. `Assign` on an Open ticket) returns 422 `TransitionNotAllowed` with the action name; only the validator keeps it out.
4. `Enum.Parse` in the handlers accepts numeric strings (`"2"`, `"1"`) for priority, action and statuses while the validators reject them (same class as UT-02 follow-ups 1-2 and UT-04 follow-up 5).
5. `TicketNumber.FromSequence(long.MaxValue)` yields 21 characters, one more than `MaxLength` 20 (same as UT-04 follow-up 2).
6. `CreateTicketCommandHandler` and `SubmitPortalTicketCommandHandler` draw the ticket number before the aggregate runs, so a refused create leaves a gap (by design per plan 15).
7. `ListTicketAgentsQueryHandler` indexes `departmentsByUser[u.Id]` for every Identity user returned, so an extra user from Identity throws `KeyNotFoundException`; it also sorts by the current culture.
8. `AssignTicketCommandHandler` treats an Identity or membership lookup failure differently: a failed user lookup does not block, a failed membership lookup is `AssigneeNotInDepartment`.
9. `TicketsDbContext.OnConfiguring` makes the context SQL-Server-only (R1), the only module context that cannot run on InMemory (if confirmed).
10. Plan/code differences otherwise: record any found between plans 15/18/47 and the code (codes, limits, status table, portal rules); none expected from the reading done during planning (the 28 codes, the transition table, the reply rules and the 14 publishing handlers match).
